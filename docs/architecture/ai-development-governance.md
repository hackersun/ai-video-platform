# AI 持续开发与代码健康治理规范

## 1. 目的

本规范用于保证 AI 视频平台在持续由 AI 和人工共同开发时，代码结构能够长期演进，而不是随着功能增加逐渐形成更大的路由、页面、方法和重复实现。

治理目标不是一次性把所有历史文件切小，而是建立一套可以持续执行的机制：

1. 新代码从第一天遵守清晰边界。
2. 存量热点只允许保持或缩小，不允许继续恶化。
3. 每次结构调整都可被测试证明为零行为变化。
4. AI 在开始修改前能快速找到业务规则的唯一所有者、公开接口和验证命令。
5. 结构规则最终由 CI 自动检查，不依赖个人记忆。

## 2. 适用范围

适用于：

- `backend/app/**` 生产代码。
- `frontend/src/**` 生产代码。
- `backend/test_*.py`、`backend/tests/**` 和 `frontend/e2e/**` 测试代码。
- 根目录脚本、CI、构建配置和架构文档。
- 所有 AI Agent、自动化脚本和人工提交。

不直接适用于第三方依赖、构建产物、缓存、媒体产物和生成代码。生成代码必须有明确目录和生成说明，不得与手写业务代码混放。

## 3. 核心原则

### 3.1 行为安全优先

- 已上线或已验证的功能、数据库数据、API 响应、工作流状态、生成任务和供应商安全门禁默认不可改变。
- 结构重构与行为变更必须分批进行。
- 结构重构必须先有现状刻画测试；测试用于证明输入、输出、持久化副作用和错误语义没有改变。
- 不为了追求目录整齐批量移动模型、路由和服务。

### 3.2 单一所有者

每条业务规则必须能回答以下问题：

- 规则由哪个模块负责？
- 对外接口是什么？
- 允许依赖哪些模块？
- 哪些测试证明规则成立？

如果同一规则出现在两个路由、页面或服务中，应先确定唯一所有者，再由其它调用方复用公开接口。

### 3.3 薄入口

FastAPI 路由只负责：

1. 接收和验证 HTTP 输入。
2. 注入用户、数据库和请求上下文。
3. 调用一个明确的应用用例。
4. 把领域错误转换为 HTTP 响应。

Next.js `page.tsx` 只负责：

1. 解析路由参数。
2. 组装 feature 组件。
3. 放置页面级 Suspense、错误边界和布局。

入口文件不得成为数据库查询、供应商协议、媒体编排或可复用业务规则的所有者。

### 3.4 棘轮治理

新代码使用严格阈值。存量代码记录当前基线，允许逐步减少，不要求一次清零。

2026-07-12 引入本规范之前已经存在的未提交产品改动必须保留并先完成稳定化，不因本规范被回退或覆盖。机器基线生成前，每个新任务以任务开始时记录的文件状态为人工比较基线；机器基线生成后，以 `baseline.json` 为唯一数值基线。

- 新违规：阻断。
- 存量违规扩大：阻断。
- 存量违规保持：允许，但修改热点时必须解释未拆分原因。
- 存量违规减少：通过。
- 例外：需要明确原因、所有者、到期条件和验证方式。

## 4. 统一量化规则

### 4.1 生产文件

| 项目 | 目标 | 硬上限 | 超限处理 |
|---|---:|---:|---|
| 新 Python/TypeScript/TSX 文件 | 300 行 | 500 行 | 拆分职责或登记例外 |
| FastAPI endpoint 模块 | 300 行 | 500 行 | schemas/use case/repository/adapter 分离 |
| FastAPI 单个路由方法 | 40 行 | 60 行 | 编排迁入 application service |
| 普通逻辑函数 | 50 行 | 80 行 | 提取有名称的规则或阶段 |
| React route page | 200 行 | 300 行 | 数据和动作迁入 feature hooks/actions |
| React feature 组件 | 120 行 | 200 行 | 拆分展示、表单、对话框或状态区 |
| 单 endpoint 模块路由数 | 8 个 | 10 个 | 按用例或资源拆 router |
| 圈复杂度 | 8 | 12 | 拆分条件策略或状态机 |
| 普通函数参数 | 4 个 | 6 个 | 使用明确的 command/context 对象 |

行数统计忽略空行和纯注释的精确策略由 `tools/code_health/policy.json` 统一定义。CI 与本规范出现冲突时，先修正规则文件和文档，不允许两套标准长期并存。

### 4.2 存量热点

- 超过 500 行的存量文件不得增加净行数。
- 超过 800 行的存量文件接收非简单功能时，必须先抽取一个职责，或把全部新逻辑写入新的聚焦模块。
- 超过 80 行的存量函数不得继续增加分支和职责。
- 对兼容入口的允许修改仅限参数适配、调用新用例、响应映射和弃用标记。
- 纯常量、声明式模型目录或自动生成文件可以登记例外，但不得在例外文件中混入运行时编排。

### 4.3 测试文件

| 项目 | 目标 | 硬上限 |
|---|---:|---:|
| Python 单元/契约测试文件 | 400 行 | 700 行 |
| Playwright spec | 350 行 | 600 行 |
| 单个测试函数 | 80 行 | 150 行 |

测试拆分按业务能力和验收责任进行，不按任意行号切割。重复的数据库、认证、API 和媒体 fixture 放入明确的 `conftest.py`、factory 或 E2E helper。

## 5. 重复代码规则

- 两处出现相同或等价的 10 行以上业务逻辑，必须确定唯一所有者。
- 不允许复制后修改的方式创建供应商协议、错误码、状态机、预算、质量门禁或实体可见性规则。
- 前后端可以分别拥有显示层规则，但后端业务真相不能在前端重新实现。
- 测试 helper 可以共享请求构造和 fixture，不共享关键断言；每个测试仍需清楚表达自身契约。
- 重复检测初期采用报告模式；建立稳定基线后，新增长重复进入阻断模式。

当前已知优先重复项：

- `workflow.py` 与 `synthesis.py` 的 source preflight 聚合。
- `characters.py`、`scripts.py`、`storyboards.py` 等处的 Qwen 配置解析。
- `shots/page.tsx` 与 `storyboards/page.tsx` 的实体引用处理。
- 多个页面的模型配置加载。
- 多个 Playwright spec 的认证 API helper。

## 6. AI Agent 修改协议

### 6.1 修改前

Agent 必须：

1. 读取 `AGENTS.md`、本规范和对应模块边界。
2. 检查 `git status`，识别用户已有改动。
3. 找到行为的当前入口、规则所有者、调用方和测试。
4. 声明意图锁、范围外事项、兼容约束、验收标准和验证命令。
5. 如果目标文件是热点，先决定新逻辑的归属，不得默认继续追加。

### 6.2 修改中

- 使用 TDD 完成行为变化。
- 一次只迁移一个用例或一个职责。
- 保持外部路由、响应字段、数据库标识、状态值和错误语义兼容。
- 不顺手重构无关代码。
- 不删除无法确认用途的兼容逻辑。
- 引入公共接口时同时写清调用方向和类型。

### 6.3 修改后

Agent 必须：

1. 运行目标测试并读取完整结果。
2. 运行代码健康检查。
3. 根据影响范围运行后端回归、前端 typecheck/build 或 Playwright。
4. 检查热点文件没有扩大、没有新增非法导入、没有新增重复规则。
5. 报告实际验证证据和未验证风险。

## 7. 变更分类

### A 类：规则与文档

- 不改变运行时行为。
- 可独立提交。
- 验证文档链接、配置格式和规则检查器测试。

### B 类：机械结构迁移

- 移动 schema、纯函数、类型和 helper。
- 必须先有刻画测试。
- 禁止同时修改业务判断。

### C 类：业务行为变化

- 使用 TDD。
- 必须列出 API、数据、UX、成本和安全影响。
- 与 B 类迁移分开提交。

### D 类：高风险基础设施或数据变化

- 包括数据库结构、鉴权、供应商调用、预算、发布和迁移。
- 必须有独立设计、回滚策略和用户确认。

## 8. CI 治理阶段

### 阶段 1：观测

- 生成当前代码健康报告。
- 记录文件、函数、路由、重复和非法依赖基线。
- CI 输出报告但暂不因存量问题失败。

### 阶段 2：棘轮

- 新文件按硬上限检查。
- 存量热点只允许持平或缩小。
- 新非法依赖和新超长函数直接失败。

### 阶段 3：收敛

- 每个功能批次减少至少一个存量违规。
- 逐步启用 TypeScript strict、复杂度和重复率阈值。
- 移除已完成治理的例外。

## 9. 例外机制

例外必须记录在 `tools/code_health/policy.json`，包含：

- 文件或规则标识。
- 当前基线值。
- 例外原因。
- 责任模块。
- 允许的最大值，不能使用无限值。
- 解除例外的完成条件。

禁止使用“历史原因”“暂时保留”而没有完成条件的例外。

## 10. 完成定义

一个治理批次只有在以下条件全部满足时才算完成：

- 行为契约没有改变，或变化已被明确批准。
- 目标测试通过。
- 相关后端/前端验证通过。
- 代码健康检查没有新增违规。
- 热点基线没有扩大。
- 文档和模块公共接口与实际代码一致。
- 没有混入用户未授权的清理或数据修改。
