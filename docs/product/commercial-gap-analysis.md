# 商用差距分析与平滑改造计划

> 审计基线：2026-08-08，分支 `codex/commercial-readiness-foundation`。
>
> 结论先行：当前系统已经具备小说、实体、资产、分镜、视频、配音、字幕、合成以及实模预算保护等完整生产链基础，但仍不满足公开收费运营要求。主要阻塞不是单个页面，而是生产鉴权、持久任务、客户计费、生产部署、可观测性和合规闭环。以下方案只做可回滚的垂直批次，不改现有 API 路径，不一次性搬目录，不重写已验证的生产编排。

## 1. 当前能力与边界

### 已具备、应保留的能力

- 小说到章节、实体、资产、剧本、分镜、视频、声音、字幕和合成的业务链已经存在。
- 系列生产运行有数据库状态、幂等键、阶段恢复、参考资产准备和供应商任务绑定。
- 实模运行有人民币预留、供应商操作记录、失败释放和结算入口。
- 项目成员已有 `owner/editor/viewer` 基础角色，部分项目 API 已执行服务端角色校验。
- 参考图已经具备持久化、对象存储出口、短期签名地址刷新和实际传入供应商的适配逻辑。
- 模型目录、能力绑定、提示词版本和认证证据已经形成独立领域模块。

这些能力是后续商用化的兼容基线。改造不得绕过模型能力契约、参考图选择、实模预算和供应商任务记账。

### 当前不能宣称的能力

- 不能宣称生产级账号安全、企业权限、可靠任务队列、客户余额或正式账单已经上线。
- 不能把“实模测试预算”当成客户计费或租户额度系统。
- 不能把 `/health` 返回静态 `healthy` 当成数据库、对象存储和队列均可用。
- 不能把本地构建通过或一次三章实模通过当成可商用结论。
- 不能在许可证、历史密钥和素材授权审计前宣称仓库可以安全公开分发。

## 2. 代码与目录现状

### 规模事实

代码健康基线覆盖约 670 个生产文件、14.7 万有效行，记录 251 个直接历史违规；当前棘轮阻止新增违规，但不自动重写历史热点。

主要热点包括：

| 路径 | 行数约值 | 风险 |
|---|---:|---|
| `backend/app/api/v1/endpoints/workflow.py` | 4,059 | HTTP、编排、媒体与状态规则混合 |
| `frontend/src/app/workflow/page.tsx` | 3,839 | 页面承担大量业务状态和请求逻辑 |
| `backend/app/api/v1/endpoints/story_bible.py` | 3,494 | 实体、审核、生成和兼容逻辑耦合 |
| `frontend/src/lib/api-client.ts` | 3,391 | 所有领域共享一个客户端巨型门面 |
| `frontend/src/app/video-generation/page.tsx` | 3,137 | 表单、任务、轮询和展示混合 |
| `backend/app/api/v1/endpoints/storyboards.py` | 2,627 | 分镜业务规则仍集中在路由层 |

### 非源码污染

- Git 已跟踪约 1,475 个音视频或图片文件，合计约 194 MB。
- 当前工作树中的 `backend/static` 约 418 MB；Git 对象包约 1.81 GiB，另有约 85 MB 垃圾对象。
- 根目录仍保留 `task_plan.md`、`findings.md`、`progress.md`、`design-qa.md`、`tmp/` 和测试输出等历史工作材料。
- 仓库没有可验证的 `LICENSE` 文件，根 `package.json` 却声明 `ISC`，法律口径不一致。

### 目录治理办法

采用“新代码进目标目录、旧入口逐步变薄”的方式：

1. 保留所有现有 HTTP 路径和数据库表。
2. 新业务放入 `backend/app/features/<能力>/`，旧 endpoint 只调用公开应用服务。
3. 前端新业务放入 `frontend/src/features/<能力>/`，旧 `page.tsx` 只做路由和布局。
4. 每次只迁移一个可验收能力，行为变更与结构迁移分开提交。
5. 生成媒体先做对象存储和归档校验，再单独取消 Git 跟踪；不能直接删除用户数据。
6. 根目录历史记录在确认无人继续依赖后迁入 `docs/archive/project-history/`。

完整目标结构和迁移规则见[仓库目录规范](../architecture/repository-layout.md)。

## 3. 商用风险登记

| 编号 | 等级 | 当前证据 | 商业影响 | 处置结论 |
|---|---|---|---|---|
| R-01 | P0 | `DEV_MODE` 默认开启；无令牌可成为 `dev-user-001`；开发模式接受未签名载荷或任意字符串 | 未授权访问和租户串数据 | 生产配置必须 fail-closed，并加入启动自检 |
| R-02 | P0 | JWT 有默认密钥；Access Token 24 小时；Refresh Token 不轮换、不撤销；前端把令牌放在 `localStorage` | XSS 后令牌可被窃取，账户无法可靠登出 | 改为短时 Access Token + HttpOnly Refresh Cookie + 会话表 |
| R-03 | P0 | 注册密码最少 6 位、立即激活；无邮箱验证、登录限流和异常登录审计 | 批量注册、撞库和账号接管 | 分批加入邮箱验证、12 位密码策略和速率限制 |
| R-04 | P0 | 项目角色校验仅覆盖部分 API；多数资源通过 `user_id` 过滤，各模块没有统一权限矩阵 | 团队协作和企业权限不可审计 | 建立组织/工作区/项目 RBAC 与路由权限合同测试 |
| R-05 | P0 | 系列执行和镜头图片轮询使用进程内 `asyncio.create_task` | 进程重启丢失执行者，多实例重复运行 | 引入持久任务队列、租约、幂等和死信恢复 |
| R-06 | P0 | `docker-compose.yml` 引用不存在的 Dockerfile、Kong 配置和 Celery 应用；包含固定示例密码并暴露基础设施端口 | 不能形成可复现生产部署 | 先建立最小生产镜像和 staging Compose，再替换兼容文件 |
| R-07 | P0 | 成本 API 的预算设置不持久化、默认返回固定额度；任务成本字段单位不统一 | 无法收费、退款、对账或处理争议 | 新增不可变用量流水，实模预算与客户账务严格分离 |
| R-08 | P0 | `/health` 只返回静态成功；没有统一请求 ID、指标、追踪、告警和受控错误日志 | 故障不可发现、不可定位、无法承诺 SLA | 增加 liveness/readiness、结构化日志、指标和告警 |
| R-09 | P0 | 全局异常响应返回 `str(exc)`，并写入通配 CORS 响应头；部分认证异常也回传原始数据库错误 | 泄露内部信息并产生不一致 CORS 行为 | 统一中文错误码，内部错误只进入脱敏日志 |
| R-10 | P0 | 后端依赖使用宽泛 `>=`；前端审计存在 1 个 critical 和 3 个 high；Next.js 固定为 14.1.0 | 构建不可复现并存在已知漏洞 | 锁定依赖并单独完成兼容升级与安全回归 |
| R-11 | P1 | 本地 `/static` 可直接公开；对象存储已支持签名出口但不是所有媒体的强制路径 | 客户素材可能越权公开或过期丢失 | 私有桶、短时签名 URL、生命周期和删除回执 |
| R-12 | P1 | 仅模型配置有专门审计事件；账号、权限、生产、退款和导出没有统一不可变审计 | 企业客户和争议处理缺证据 | 建立租户级审计事件模型与只读查询 |
| R-13 | P1 | 登录、注册、找回、重置各自硬编码暗色布局；登录成功人为等待 1 秒 | 品牌不统一、移动端信息弱、操作反馈迟缓 | 抽取 AuthShell，统一状态与无障碍规则 |
| R-14 | P1 | 没有隐私政策、服务条款、版权申诉、数据导出删除和素材授权台账 | 不能稳妥公开收费运营 | 产品、法务和技术共同完成合规闭环 |
| R-15 | P1 | 仓库公开、无 LICENSE，且历史中存在大量媒体与长期分叉旧 `dev` | 知识产权、隐私和协作风险 | 保持可见性不变，先完成历史扫描和许可证决策 |

## 4. 平滑改造批次

### 批次 0：治理地基（本分支）

**目标**：先建立不改变生产行为的约束和证据。

- 已建立目录规范、三线分支规范、商业门禁和安全基线。
- 已建立代码健康棘轮、基线和 CI 报告。
- 已增加 CODEOWNERS、PR 模板和 Dependabot 配置。
- 已修复初始化脚本的 PostgreSQL JSON 方言问题。
- 已把旧远端 `dev` 原样归档到 `archive/dev-legacy-20260808`。

**退出门槛**：SQLite 后端、PostgreSQL 后端、前端构建和代码健康均通过；通过 PR 进入主线后再重建 `dev` 与 `releases`。

### 批次 1：可复现部署与迁移

**意图锁定**：相同提交、相同配置得到相同镜像和数据库结构。

**改动范围**：

- 增加多阶段 `frontend/Dockerfile`、`backend/Dockerfile` 和 `.dockerignore`。
- 把当前 Compose 标记为开发兼容入口；新增 `infra/compose/staging.yml` 和 `infra/compose/production.yml`。
- 删除生产拓扑中的示例密码、主机端口直出和源码卷挂载。
- 引入 Alembic，先以“标记现状”方式接管已有表，再逐个迁移兼容函数。
- 后端依赖生成锁文件或带哈希约束；前端锁文件由 CI 冻结安装。

**兼容边界**：不修改 API 地址、表名或当前本地 SQLite 启动方式。

**验证**：全新空库初始化、已有 SQLite 升级副本、PostgreSQL 升级副本、镜像冷启动、回滚镜像和数据库恢复演练。

**回滚**：旧 `init_db.py` 在两个候选版本内作为只读兼容检查保留；失败时回退镜像并恢复迁移前快照。

### 批次 2：账号与会话安全

**意图锁定**：生产环境中，没有有效会话就不能读取任何客户资源。

**改动范围**：

- 增加明确 `APP_ENV=local/test/staging/production`；只有 local/test 可启用开发用户。
- 生产启动时强制 JWT、加密、数据库和对象存储配置，缺失即退出。
- Access Token 缩短到 10-15 分钟；Refresh Token 只存 HttpOnly、Secure、SameSite Cookie。
- 新建 `user_sessions`，只存 Refresh Token 哈希、设备摘要、过期、轮换和撤销状态。
- 密码最少 12 位，加入弱密码检查；注册进入 `pending_verification`，邮箱验证后激活。
- 登录、注册、找回和重置分别限流；同一返回文案避免枚举账号。

**兼容边界**：保留 Bearer Access Token 支持一个迁移周期；旧前端可登录，但响应附带迁移提示，不能无限期兼容开发令牌。

**数据迁移**：现有激活用户不强制重验邮箱，但首次敏感操作前确认邮箱；旧 Refresh Token 在灰度窗口后全部撤销。

**验证**：匿名、伪造、过期、轮换复用、登出、改密撤销、跨设备和并发刷新测试；生产配置缺失启动失败测试。

### 批次 3：组织、工作区和项目权限

**意图锁定**：所有资源访问由一个服务端权限模型判定，前端只展示结果。

**目标模型**：

```text
平台管理员
  └── 组织 owner / billing
        └── 工作区 admin / member
              └── 项目 owner / editor / reviewer / viewer
```

**改动范围**：

- 在现有 `ProjectMember` 之上增加组织和工作区，不重建已有项目。
- 为没有组织的现有用户自动创建“个人组织”，原项目归入该组织。
- 建立机器可读 API 权限矩阵：匿名、登录、组织角色、项目角色、平台角色。
- `user_id` 继续作为数据隔离字段，但授权入口统一到权限服务；所有资源必须验证项目归属链。
- 增加 reviewer 和 billing，平台管理员默认不得查看客户正文。

**验证**：每个资源执行 owner/editor/reviewer/viewer、非成员、跨组织和停用成员的正反向合同测试；响应继续用 404 隐藏无权资源。

**回滚**：保留现有 owner/editor/viewer 映射；组织功能可由开关隐藏，但服务端隔离校验不能关闭。

### 批次 4：持久任务与恢复

**意图锁定**：服务重启、扩容或供应商超时不会丢任务，也不会重复付费提交。

**改动范围**：

- 先封装 `TaskDispatcher`，默认实现继续调用当前进程内执行器，避免一次性替换。
- 新增持久 `task_executions`：幂等键、租约拥有者、租约到期、尝试次数、下一次执行、供应商任务 ID 和终态。
- 第二阶段接入 Redis + worker；Web 进程只提交任务，不执行长任务。
- 供应商已接受后只轮询状态；不确定状态进入人工确认，不自动再次扣费提交。
- 超时任务进入死信，中文显示“等待供应商”“需要人工确认”“可安全重试”等动作。

**兼容边界**：现有 VideoJob、ImageJob、TTSJob、BatchJob 和 SeriesProductionRun 保持业务真相；任务表只承载执行调度。

**验证**：在提交前、供应商接受后、持久化结果前分别杀进程；验证恢复、单次扣费、单个产物和可解释状态。

### 批次 5：客户用量、额度和财务流水

**意图锁定**：任何收费、扣减、释放和退款都有不可变、可对账的人民币证据。

**账务模型**：

- `usage_events`：模型、输入输出量、供应商任务、实际费用、租户、项目和幂等键。
- `ledger_entries`：预扣、结算、释放、退款、人工调整；使用 Decimal 和统一人民币分或 Decimal 元。
- `wallets/quotas`：客户余额、套餐额度、项目预算和并发限制。
- `provider_reconciliations`：供应商账单与内部用量差异。

**规则**：实模验收预算继续独立存在；管理员可选择测试资金来源，但不能用“关闭测试预算”绕过客户余额、并发和供应商安全限制。

**验证**：并发预扣、重复回调、失败释放、部分结算、退款、余额不足、月底对账和 Decimal 精度测试。财务流水只允许冲正，不允许覆盖历史。

### 批次 6：私有媒体与数据生命周期

**意图锁定**：客户原文和媒体默认不可公开，仍能可靠交给供应商和播放器。

**改动范围**：

- 以已有媒体持久化和七牛签名出口为唯一媒体交付门面。
- 原始素材、过程资产和成片使用不同前缀、权限和保留期。
- 客户播放使用短时签名地址；供应商需要公网参考图时生成范围受限、短时有效地址并记录实际输入清单。
- 本地 `/static` 仅用于 local/test；生产不挂载用户媒体。
- 增加删除队列、删除回执、备份保留和法律保留状态。

**迁移**：先复制和校验哈希，再切换数据库 URL，经过一个版本观察后才取消 Git 跟踪或清理本地文件。

**验证**：跨租户访问、过期、刷新、供应商抓取、对象丢失、删除和备份恢复测试。

### 批次 7：登录、注册与首页体验

**意图锁定**：新用户能在 30 秒内理解产品、完成安全登录，并清楚知道下一步。

#### 统一 AuthShell

- 桌面使用约 `44% / 56%` 的品牌说明与表单分栏，表单最大宽度 440 px。
- 移动端只保留紧凑品牌头、标题、表单和帮助入口，不直接隐藏全部产品价值说明。
- 只保留一套背景、Logo、主按钮、错误/成功提示和页脚；登录、注册、找回、重置共用。
- 支持浅色/深色设计令牌，不在页面硬编码整套 `slate-950` 或另一套 violet 渐变。
- 删除登录成功后的 1 秒人工等待；令牌建立后立即导航，并为重复提交加互斥状态。

#### 信息结构

登录页：

1. 标题“登录并继续制作”。
2. 用户名或邮箱、密码、显示密码、忘记密码。
3. 主按钮“登录”。
4. 企业登录扩展位和支持入口。
5. 不再展示尚未实现的权限或安全承诺。

注册页：

1. 邮箱、显示名称、密码强度和确认条款。
2. 明确“验证邮箱后启用账号”。
3. 隐私政策、服务条款和素材版权提示。

首页：

- 第一屏只说明“小说到可交付视频”的核心价值和一个主行动。
- 展示真实且获授权的样片、标准流程、支持输入输出、价格口径、版权边界和服务状态。
- 未上线的 SLA、企业权限或模型能力不得作为营销承诺。

**验证**：360/390/768/1440 px 视觉基线、键盘顺序、焦点、错误朗读、慢网、重复提交和登录重定向 E2E；输出关键页面截图作为发布证据。

### 批次 8：可观测性、支持和运营

**意图锁定**：客户发现问题前，运营能知道哪一租户、哪一步、哪个供应商出了什么问题。

- 每个请求、生产运行和供应商任务建立关联 ID。
- `/health/live` 只表示进程存活；`/health/ready` 检查数据库、队列和必要配置。
- 指标至少包括请求错误率、队列深度、任务耗时、供应商成功率、重复提交拦截、费用差异和媒体交付失败。
- 日志使用结构化字段并脱敏，不回传原始堆栈和密钥。
- 建立 P0/P1/P2 告警、值班联系人、事故模板、状态页和客户支持工单关联。
- 每个版本做一次恢复演练和一次三章付费实模验收，但实模通过只是发布门禁的一部分。

## 5. 推荐执行顺序

| 阶段 | 批次 | 依赖 | 可交付结果 |
|---|---|---|---|
| 基础 | 0、1 | 无 | 可审查主线、可复现 staging、可靠迁移 |
| 安全 | 2、3 | 1 | 可收费前的账号与租户隔离 |
| 可靠性 | 4、6 | 1、3 | 可恢复任务和私有媒体交付 |
| 财务 | 5 | 3、4 | 可审计的额度、费用、退款和对账 |
| 体验 | 7 | 2、3 | 统一登录、注册、首页和清晰中文状态 |
| 运营 | 8 | 1、4、5 | 监控、告警、支持和发布证据闭环 |

阶段不是固定日历承诺。每个批次必须在 staging 完成数据迁移、回滚和目标负载验证后，才能估算生产发布时间。

## 6. 每批统一验收模板

每个 PR 必须回答：

1. **意图锁定**：本批只解决什么问题。
2. **范围边界**：哪些 API、数据、流程明确不改变。
3. **数据迁移**：新旧数据如何同时读、如何切换、如何回退。
4. **安全影响**：匿名、跨租户、角色和密钥如何验证。
5. **费用影响**：是否可能重复提交、漏记、错记或无法退款。
6. **运行证据**：目标测试、完整测试、构建、数据库和截图或日志。
7. **回滚证据**：镜像、迁移、配置和开关如何恢复。

任一 P0 门禁未通过时，产品可以继续内测和实模验收，但不得标记为“可公开收费运营”。
