# 可持续 AI 开发与代码健康治理设计

## 意图锁

在不改变现有产品功能、运行数据、API 契约和生产安全门禁的前提下，建立能够阻止大文件、大方法、重复业务规则和错误依赖继续增长的项目治理体系，并为后续逐业务用例拆分提供统一边界。

## 已确认现状

- `backend/app` 当前约 8.1 万行，17 个生产文件超过 1000 行，6 个超过 2000 行。
- `frontend/src` 当前约 5.85 万行，16 个生产文件超过 1000 行，8 个超过 2000 行。
- `backend/app/api/v1/endpoints/workflow.py` 为 6191 行，`generate_workflow_media_batch()` 为 1035 行。
- `frontend/src/lib/api-client.ts` 为 3309 行，`ApiClient` 单类约 2797 行、317 个成员。
- 多个 React 页面核心组件超过 1700 行。
- 已存在 endpoint 调用 endpoint、service 反向导入 endpoint 和服务循环依赖。
- CI 当前执行后端测试、前端 typecheck 和 build，但不检查文件规模、方法规模、复杂度、重复率和依赖边界。
- 当前工作区存在大量未提交业务改动，因此治理实现不得覆盖或混入这些改动。

## 范围

本设计包含：

- 项目统一代码健康规则。
- 后端和前端模块分类与允许依赖。
- 新代码严格阈值和存量棘轮。
- 例外登记机制。
- 代码健康扫描器、基线和 CI 接入设计。
- 后续后端、前端和测试拆分路线。

本设计不包含：

- 本阶段直接拆分任何巨型业务文件。
- 改变数据库表、API、用户界面或供应商行为。
- 一次性启用全仓 TypeScript strict。
- 一次性消除所有重复或复杂度违规。
- 清理当前未提交业务工作。

## 方案比较

### 方案 A：只写规范

成本最低，但无法阻止 AI 继续向热点追加代码。不能满足持续治理目标。

### 方案 B：规范、机器棘轮、按触碰迁移

先记录存量，再阻止新增违规；后续修改热点时按用例迁移。风险可控，可持续执行，推荐采用。

### 方案 C：一次性垂直模块重写

最终目录最整齐，但当前功能和工作区变更较多，回归和合并风险过高。本阶段不采用。

## 设计决策

采用方案 B。

规则真相源：

- 人可读规则：`docs/architecture/ai-development-governance.md`。
- 模块边界：`docs/architecture/module-boundaries.md`。
- Agent 必读摘要：根 `AGENTS.md`。
- 机器可读规则：未来的 `tools/code_health/policy.json`。
- 存量快照：未来的 `tools/code_health/baseline.json`。

## 代码健康检查设计

第一阶段使用 Python 标准库实现仓库扫描器，避免一开始引入多个质量工具：

- 统计生产文件有效行数。
- 使用 Python AST 统计函数长度、路由数和非法 import。
- 使用 TypeScript compiler API 统计 TS/TSX 函数和组件长度；如果依赖不可用则明确失败，不静默跳过。
- 根据 `policy.json` 对新文件执行硬限制。
- 根据 `baseline.json` 对存量违规执行只降不升。
- 输出人可读表格和 JSON 报告。

重复率在第一阶段以报告模式接入。依赖边界、文件增长和新增长方法从棘轮启用时直接阻断。

## 基线生成条件

不得在当前混杂的活动工作区随意生成正式基线。正式基线必须满足以下之一：

1. 当前业务批次已提交，目标分支工作区干净；或
2. 用户明确指定某个提交为治理基线。

基线记录文件路径、文件有效行数、函数最大长度、路由数和已知例外。它不是永久豁免；数值只能保持或下降。

## CI 策略

1. 报告阶段：生成报告，不阻断存量问题。
2. 棘轮阶段：阻断新违规、存量扩大和非法依赖新增。
3. 收敛阶段：逐批降低基线并移除例外。

CI 命令统一为：

```bash
npm run verify:code-health
```

该命令不得修改源文件、数据库、媒体目录或配置文件。

## 后续拆分策略

每个巨型入口按“一个用例一个批次”处理。例如 `workflow.py` 不按任意行数拆成多个 helper 文件，而按以下能力拆分：

- 工作流媒体生成。
- 质量评估与最小修复。
- 状态查询与时间线同步。
- 渲染包构建。
- 视频拼接。
- 外部媒体和 FFmpeg adapter。

原 FastAPI 路由保持 URL、请求和响应兼容，只调用新的应用用例。

前端页面按数据、动作和显示职责拆分：

- 领域 API client。
- 页面用例 hook。
- 用户 action。
- 状态面板、表单、对话框和列表组件。
- route page 只保留组装。

## 风险与控制

### 基线固化坏结构

控制：基线仅允许下降；热点修改必须优先提取职责。

### 机械拆分产生更多碎片

控制：按业务用例拆分，每个模块必须有清晰公开接口和独立测试。

### 重构改变隐藏行为

控制：先写刻画测试，结构和行为分批提交，保留兼容入口。

### CI 一次启用导致全仓失败

控制：观测、棘轮、收敛三阶段推进。

### 当前工作区改动被覆盖

控制：治理工具初期只创建新文件；修改现有 package/CI 前必须重新读取 diff，并在稳定基线上执行。

## 验收标准

- 根 `AGENTS.md` 明确引用统一规则并包含不可协商摘要。
- 人可读规则和模块边界文档存在且互不矛盾。
- 代码健康工具具有自动化测试。
- 新文件超限会失败。
- 存量热点扩大时会失败，缩小时会通过。
- endpoint-to-endpoint、service-to-endpoint 新依赖会失败。
- CI 可以生成可审计报告，且不修改工作区。
- 正式基线只在稳定提交上生成。
- 后续每个拆分批次都有独立设计、行为契约和验证命令。
