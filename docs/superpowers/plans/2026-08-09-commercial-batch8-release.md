# 商业发布候选收口 Implementation Plan

**Goal:** 为最新 `dev` 增加可验证的运行健康、安全扫描和发布证据，使其可以安全进入 `releases` 候选线，同时诚实保留必须由 staging、法务或运营提供的外部门禁。

## Execution Contract

**Intent Lock:** 每个候选提交都能回答“服务是否真的可用、请求如何追踪、依赖是否存在高危漏洞、哪些外部门禁仍未完成”。

**Out of Scope:** 不调用付费模型、不删除历史媒体、不选择项目许可证、不伪造备份恢复、人工 UAT 或 staging 审批证据、不直接提升到 `main`。

**Constraints:**

- 保留 `/health` 兼容响应；新增探针不能泄露数据库地址、密钥或异常堆栈。
- readiness 必须检查真实数据库连接和持久任务队列，失败返回 503 与中文直白说明。
- 每个响应带可追踪请求 ID；指标只使用路由模板等低基数字段。
- 指标端点在 staging/production 必须受运营令牌保护。
- 安全扫描固定工具版本，高危或严重漏洞必须阻断 CI。
- 不移动现有生产目录，不扩大历史热点，不改变现有业务 API。

**Acceptance Criteria:**

1. `/health/live` 只证明进程存活；`/health/ready` 真实检查数据库与任务队列并能安全失败。
2. 正常和异常响应均包含 `X-Request-ID`，500 响应包含可提供给客服的请求编号。
3. `/metrics` 输出低基数 Prometheus 文本，正式环境无令牌时拒绝访问。
4. CI 增加前端依赖、后端依赖和已跟踪敏感文件扫描，任何高危结果阻断合并。
5. 完整后端、PostgreSQL、前端、代码健康、E2E、Docker 与 Compose 验证通过。
6. 生成绑定提交、镜像摘要、性能冒烟和剩余外部门禁的中文发布证据。
7. 通过 PR 合入 `dev`，再以 `dev -> releases` PR 建立候选版本；`main` 不提前变更。
